Refill

An empty chair is money walking out of the salon. Refill offers the cancelled slot to the next waiting customer who fits it, checks consent before every message, and never books two people into one chair.

Open the live app Open the Lab GitHub repo

What we built, in one minute

  1. Choose "Try the demo", then "Front desk". Open a future appointment, choose "Record a cancellation", and confirm "Yes, [client name] cancelled".
  2. Open the amber gap. Review matching clients and "Not offered, and why", then use Send offers (for example, "Send 3 offers"). The database re-checks every rule.
  3. The client opens a pending offer here or by phone QR code: "Book" with the offered time, "Not today", or "Stop messages from Kesar Salon".
  4. Two taps at once: one booking. The other customer keeps their queue place.
  5. "Front desk" → "Activity" records the decisions. Its "CSV" and "JSON" buttons export the evidence; "Owner" → "Overview" shows recovery.
  6. "Proof" opens the Lab: case checks, editable inputs and before/after results. The view menu calls it "Proof for judges".

How it works

Rules engine

src/engine.ts

Pure functions. For each free slot it checks every waitlist entry in this order and stops at the first failure: consent → skill → duration → availability. Free slots are filled in order; each takes the first eligible person in the queue; nobody gets two slots.

Database

Supabase Postgres

Every table has row level security on and no policies, so the public key cannot read or write tables. The browser can only call 12 functions, and each one re-checks the rules. The page's suggestions are never trusted.

No double booking

accept_offer

Locks the offer, then the slot, then the customer, in that order everywhere. Simultaneous taps queue on the slot lock: the first finds it free and books; the rest find it booked and keep their place. A partial unique index is the last line of defence.

Front end

React + Vite + TypeScript

Role-specific views: Front desk, Owner, Staff and Client, plus Proof for the Lab. Clients also have private offer and reschedule pages. The app talks to the database with plain fetch and refreshes live state periodically. Installable as an app; works on phones.

Questions judges will ask

How do you guarantee two people never get the same slot?

The booking happens inside one database transaction that locks the slot row. Concurrent taps wait in line. The first finds the slot free; everyone after finds it booked and is told which booking won. A unique index on confirmed bookings per slot backs it up. We test it with 8 and 12 simultaneous taps against the live database.

Why not check availability in the app before booking?

Two phones can both see "free" at the same moment. Only the database can serialise them. The page previews; the database decides.

What if a customer taps Accept twice?

The second tap returns ALREADY_CONFIRMED with the same booking number. Idempotent: one booking.

What does consent mean in your system?

Yes, no or unknown, with a timestamp and a source. Unknown is never treated as yes. It is checked when the offer is sent and again right before the booking, so withdrawing consent between the two stops it. A STOP from the customer revokes every open offer.

Can someone bypass the page and write to your tables?

No. Row level security is on with no policies. The public key can only call the 12 functions, and each one validates its inputs and re-checks the rules. Supabase's linter lists those functions as callable by anyone; that is intentional, they are the API.

Is it protected against abuse or a DDoS?

The site is static on Vercel's edge network, which absorbs network-level floods. The database enforces its own limits per IP, per demo day and per offer (for example 240 writes a minute per day, 600 taps a minute per IP), caps payload and text sizes, revokes all direct table access from the public key and deletes demo days after 3 days. npm run dbtest proves each limit against the live database.

What if nobody replies to an offer?

Every offer holds for 15 minutes (never past the slot's start). Then it lapses, the log says so, and the desk suggests the next people in the queue. Nobody is messaged more than 3 times a day.

What happens with a bad input file?

It stops with a code (duplicate id, missing field, invalid value) and the exact location. A bad file never produces a half-right answer. Try it in the Lab.

What if two judges use the app at once?

Each visitor gets a separate workspace (a uuid in the link). Share the link to open the same day on a phone.

How do you know your rules are right?

The organiser's fixture reproduces its expected match (W1 → S2). 18 core scenarios plus the team's own file run on every push in CI, and live in the Lab.

What does it not do yet?

No owner login, no real WhatsApp/SMS sending, polling instead of a live socket, synthetic data only. All listed in the README and KNOWN_LIMITS.

Late cancellationMove the demo clock, cancel an appointment inside 2 hours: tagged LATE, offers still go out; inside 10 minutes nothing is offered. Lab toggle "Late cancellation" with before/after export.
